## Architecture and verification implications

- Add a bounded study-tools domain module and router rather than another large block in `platform.js` or the server factory. Current composition points: `services/platform/index.js:9-18,33-34`; authenticated middleware at `routes.js:39-60`; new page modules can mount within the existing panels. All new strings belong in complete AR/EN copy; use logical CSS and current tokens.
- Validate IDs and ownership on the server. Follow user row lock (`common.js:25-27`) for idempotent task/routine changes and circle lock/membership (`cohorts.js:105-113`) for shared changes. Bound lengths, collection counts, schedule horizons and query ranges. Calendar/link/resource output needs proper escaping and only supported URL schemes.
- Schema changes must include account deletion via foreign-key cascades, current-member access removal, and backup/restore. `services/platform/maintenance.js:5-9` hardcodes table order; `30-34` validates exact v1/v2 table counts. Introduce a versioned compatible snapshot format; adding tables to a migration alone would omit them from backups or break old restores. `database.js:104-105` currently checks version 3 explicitly.
- Credit attribution, goals, charts and challenges must read canonical credited sessions/ledger. Existing `focus_sessions.daily_ms` is the Riyadh split (`progress.js:9-26`); completed sessions alone feed current totals. Rest, import, notes, RSVP, calendar attendance, camera and paid status must not create reward credit.
- Minimum evidence for each chosen row: a real user UI flow, persistence/reload, edit/reversal or completion, empty/error behavior, second-user denied access, and focused regression coverage. For recurring/RSVP/challenge features also prove duplicate/retry and time-window behavior. Parent owns final browser checks at mobile/desktop, AR/EN, light/dark, and the complete applicable gate on the exact delivered source.
