# Private planner and circle extension boundaries

Read-only source audit, 2026-10-22 (Asia/Riyadh). Branch `feat/2026-10-22-top-20`, base `3091b0eefd0461163a15861d7fd67ddeb868e739`. No app/test edits, probes, broad test gates, production credentials or external actions. This is an implementation guard map for proposed features, not a claim that those features already exist or that new defects were reproduced.

## Safe seams

Add a small SQL-backed planner service next to `progress` and `cohorts`, initialized in `services/platform/index.js:32-34`; keep private planner rules out of the room socket monolith. Register its account endpoints after `services/platform/routes.js:39-60`, preserving authentication, current-object/epoch checks, guarded Supabase compatibility projection, no-store responses and mutation limits. `routes.js:14-21` is the existing structured error/unavailable boundary. The real server wires live identity at `co-study-server.js:872-873`; do not replace it with a stale account object or assume local accounts always use the SQL record store.

Use the current circle service membership policy (`services/platform/cohorts.js:6-11`) for resources/RSVP/calendar; a UI-hidden control is not permission. Keep billing, named staff permissions and verified focus rewards independent of planner/task completion, routine checks, goals and RSVP.

## Ownership and row-scope requirements

| Extension | Server and SQL guard | Concrete integration hazard |
| --- | --- | --- |
| Projects/tasks/private notes | Actor user ID comes only from authenticated context. All SELECT/UPDATE/DELETE predicates include owner ID. User FK must cascade. A task's project must belong to the same owner; enforce by scoped lookup and preferably a composite owner/project FK. | A globally valid project ID alone can attach A's task to B's project. Generic PATCH or client-supplied userId can become an IDOR. Empty patch/state transitions must not reset unrelated fields. |
| Routines, personal goals and daily plans | Store per-user preferences separately from earned progress. Validate target range, day keys and timezone. Date-only due days and UTC instants need distinct fields/contracts. | Browser-local midnight differs from fixed Riyadh reward days. An editable goal or checked routine must not manufacture a verified session or rewrite a streak. |
| Session history/annotations | Scope referenced focus session by both id and user. Metadata may be edited independently; credited_ms, daily_ms, xp, state and ledger remain owned by `progress.js`. | A new general history endpoint that accepts minutes or arbitrary session state bypasses trusted accounting. Deleting a task/project must not cascade into verified focus history or XP. |
| Room bookmarks | Private owner-scoped row; do not store room passwords or invite bearer codes. Re-evaluate runtime room existence plus `platform.canJoin` when exposing a current room link/name. Preserve normal password checks at admission. | Bookmarks confer no room authority. `platform.canJoin` returns true for an absent/unscoped SQL room (`index.js:58-68`); combine with runtime existence as `dashboard.js:7-10,27-30` does. A once-public room can later become private. |
| Circle resources | Read requires current active membership. Mutations need an explicit policy, such as owner/supervisor, evaluated in the same transaction as the target write. Scope resource id to cohort id. Use bounded sanitized text/URLs and textContent on render. | Querying by resource id after checking a different circle leaks shared content. Do not fetch arbitrary submitted URLs server-side; external links need an allowed protocol and safe new-window behavior. Private personal notes must never be copied into shared resources implicitly. |
| RSVP | Actor changes only their own response. Validate session belongs to the requested active circle. Unique(session_id,user_id); allowed response values explicit. Decide ordinary-member detail visibility; self plus real aggregate counts fits the existing self-only attendance policy (`cohorts.js:169-180`). | Joining a valid session ID to the wrong circle is an IDOR. Member removal leaves the user account alive, so user FK cascade alone does not remove their old RSVP; exclude removed members from current counts/access or explicitly clean membership-scoped responses on leave/remove. RSVP is intention, not attendance or focus proof. |
| Calendar download | Authenticated on-demand export filtered by current active membership. Include only chosen session metadata; safe text/line escaping and bounded output. Use a local file download, not a public bearer subscription URL. | A reusable unauthenticated calendar URL can outlive circle removal. Do not export passwords, invitation tokens, participant emails, private notes or other people's RSVP details. Calendar file content remains with its recipient after download. |

For cross-owner/cross-circle references, plain FKs establish existence, not matching ownership. If a composite FK is used, add the matching UNIQUE key on the parent first. Parent deletion policy should be deliberate: private descendants cascade; optional task/project links on focus metadata can become null; shared resource authors may become null or their contributions may be removed according to the chosen product contract. Do not strand personal note text under an author-null shared row.

## Migration, deletion and transaction hazards

1. **Register the migration and change the runtime version gate together.** `services/platform/database.js:98-105` explicitly lists three migration files and requires version 3. Adding a SQL file alone does nothing. PGlite auto-migrates locally; PostgreSQL runtime intentionally does not migrate without the explicit maintenance mode (`database.js:97-101`; `scripts/platform-maintenance.js:21`). Preserve that external migration boundary. Keep new migrations additive/idempotent and prove upgrade from populated v3, not only empty database creation.
2. **Expand backup/restore without invalidating existing snapshots.** `services/platform/maintenance.js:5-9` is a fixed table allowlist; new tables otherwise silently disappear from backups. `:17,30-34` embeds v2 and checks exact table counts. Introduce a new snapshot format with its own full list while retaining the exact historical v1/v2 sets. Restore parents before dependent planner/RSVP rows (`:39-47`), and keep account epoch rotation (`:42`). Round-trip nonempty new tables and load an old-format snapshot into the new schema.
3. **Make account deletion reach every new personal table.** Normal SQL-store deletion invokes `platform.purgeUser` transactionally (`record-store.js:48-51`), and `platform/index.js:99-104` archives owned circles then deletes the user row. Auth deletion also supports the separate Supabase account backend (`auth-routes.js:295-317`). New private tables should cascade from `halastudy.users`; shared author references need an explicit deletion policy. Do not put planner authority only inside account payload JSON or only in browser storage.
4. **Use one domain lock order.** Private aggregate mutations can use `common.js:25-27` user lock, then project/task rows. Circle writes already lock cohort first (`cohorts.js:36,91,107,142,152,161`), then target rows and `membership(..., tx)`. Do not add user→cohort locking without reconciling deletion's cohort→user path (`index.js:99-104`); that can introduce an avoidable opposite lock order. Reads that determine quotas and their insert must share the lock/transaction.
5. **A lost response is not a failed commit.** Give creates/imports/routine instantiation a stable idempotency key scoped to the owner and operation, or a stable caller UUID with matching-request checks. Use unique keys for bookmark/RSVP duplicates. For PATCH/reorder, add a revision/expected-version contract if two tabs can overwrite one another; a process-local JS queue alone does not protect SQL changes. Report conflict instead of acknowledging an overwritten draft.
6. **Keep SQL writes atomic and bounded.** New factories must use the supplied tx for every query inside a transaction, not `db.query` mid-operation. PostgreSQL has a small pool and explicit lock/query deadlines (`database.js:14-18`); nested independent transactions can exhaust it. Preserve the single-runtime lease (`:23-41`) and PGlite filesystem lock (`:75-80`), rather than assuming new services justify replicas. Bound collection sizes, JSON arrays, text lengths and export sizes; paginate history instead of unbounded scans.

## Verified-focus and time boundary

`services/platform/progress.js:28-76` owns the server-timed session and its transactional award. It locks the account, scopes the focus row by user, deduplicates complete, excludes pause/interruption time, and caps reward credit. `db/migrations/001-platform.sql:112-118` enforces one open session and unique session/day/rule ledger rows. Preserve these invariants while adding task selection, project tags, recaps or calendar links.

- Link a selected task only after checking its owner; add metadata at server start or through a separate scoped metadata endpoint. A task deleted or completed in another tab must produce a useful unassigned/retry state rather than breaking the focus heartbeat.
- Imported/manual history, offline work, task checkboxes, due-date completion, routines, RSVP, camera status and purchases must not write verified ledger rows. Editable self-reported history must retain its source label.
- The day helper is intentionally fixed to Riyadh (`common.js:15-16`); schedule formatting uses the device's named timezone (`public/js/schedule-display.js:2-8`). Keep these concepts visible and separate. Store UTC instants for calendar sessions, and handle invalid dates/DST ambiguity when expanding routines into future instants.
- Preserve idempotent completion and pending-ID recovery in `public/js/focus-client.js:26-64`; do not complete/restart a focus session simply because a task selection or planner panel changes. History remains bounded by its existing entitlement window (`progress.js:82-84`), so private annotation reads should not unintentionally expose older verified rows through a new free endpoint.

## Client/offline boundary

`public/js/halastudy-core.js:145-172` provides acknowledged JSON requests with a 15-second abort; errors remain distinguishable from zero/empty. Reuse that contract. The cached identity promise (`:176-198`) can be stale after another tab logs out, so an offline queue must revalidate identity before replay and bind each item to its original user ID. Never replay one account's drafts under another account's cookie.

Keep unsaved state in a dedicated planner module with per-user/per-resource keys, expiry and explicit saved/unsaved/conflict feedback. Storage access must tolerate denied/corrupt storage. Clear private drafts and queued payloads on successful signout/deletion. Avoid storing complete server collections as permanent shared-device localStorage caches. Read-only stale data must be labeled and must never enable an unauthorized mutation. Offline operation does not authorize offline XP.

Use request generations for planner/project/circle selection as `public/js/platform.js:200-209` already does for circle panels. `platform.js:481-484` currently refreshes all account state and directly restores focus state; avoid adding planner mutations that trigger this broad refresh and overwrite an independent active draft or focus state with an older response. Reconcile the narrow affected collection. Preserve `#main` skip-link handling and Back/Forward/hash behavior (`:502-510`) when adding a planner panel. Render user content as text, and keep new copy fully Arabic/English.
